## 雰囲気

時間帯（朝・昼・夕・夜）、季節、天気、場所の種類（寺社・公園・海辺・街中など）から「今の雰囲気」を決め、画面・音・話し方をそろえて変える。背景画像・背景音はこの「雰囲気」を入力として使う想定。

- [ ] 雰囲気を表すモデルを作る（例: `Mood` = 時間帯 × 天気 × 場所の種類）
- [ ] 画面の配色・フォントの切り替え（夜は暗め、雨は寒色など）
- [ ] 話しかけのトーンに反映する（プロンプト変数に雰囲気を渡す）
- [ ] 設定でオン・オフ

実装の手がかり:
- 時間帯・季節は `WalkCompanion` の `timeOfDay` / `season`（private）にある。`Mood` に切り出して共通にする
- 天気は `Weather.code`（WMO コード）と `WeatherCodes` で分類できる
- 天気は今は `WalkService` の中にしかない。画面から使うには `CompanionFeed` のような共有の StateFlow に載せる。散策モード外は時間帯・季節だけで決める
- 場所の種類は `Poi.category`（神社・寺院・公園など）の多数決で推定できる。海辺は Overpass に `natural=beach|coastline` を足す必要がある

決めること:
- 場所の種類をどう判定するか（周辺スポットのタグから推定する、地図の土地利用を使う、など）
- 雰囲気が頻繁に切り替わらないようにする間隔（天気は 15 分ごとの取得。場所の種類は数分続いたら切り替える、など）

## 背景画像

散策中のメイン画面の背景に、雰囲気や近くのスポットに合った画像を表示する。

- [ ] 画像の出どころを決める（下記）
- [ ] 地図との共存（半透明にする、散策中だけ地図を小さくする、など）
- [ ] 近くのスポットの写真を表示する（Wikimedia Commons など。スポットの `wikidata` タグ → P18 の画像）
- [ ] 通信量を抑える（Wi-Fi 時のみ取得、キャッシュ）

画像の出どころの候補:
- アプリに同梱するイラスト・写真（雰囲気ごとに数枚）。まずはここから始める
- Wikimedia Commons（スポットの写真。ライセンス表示が必要）
- 画像生成 AI（費用・生成時間・品質のばらつきが課題）

決めること:
- 優先度: 「歩きながら画面を見させない」（共通の検討事項）と方向が逆なので、★のままにするか、散策モードで画面を開いたときの演出程度にとどめるか
- ライセンス表示の場所と方法
- 画像があると地図が見にくくならないか

## 背景音

雰囲気に合わせた環境音（鳥の声、波、雨音、寺の鐘など）や BGM を流す。

- [ ] （先に）読み上げ（`Speaker`）でオーディオフォーカス（`AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`）を取る。今は取っていないため、ユーザーが聴いている音楽に読み上げが重なる。背景音がなくても役立つ小さな修正
- [ ] 音源を用意する（同梱、またはライセンスの明確な素材。OGG のループで 6〜8 種類程度から）
- [ ] 読み上げ中は背景音の音量を下げる（自分のアプリの音はオーディオフォーカスでは下がらないので、`UtteranceProgressListener` の開始・終了で音量を上げ下げする）
- [ ] 他のアプリの音楽再生との共存（`AudioManager.isMusicActive` のときは流さない、を既定にする）
- [ ] 音量・オン・オフの設定
- [ ] バックグラウンド（散策モードのフォアグラウンドサービス）での再生

決めること:
- イヤホンがないときの扱い（スピーカーから流すか）
- 周囲の音が聞こえにくくなる安全面の配慮（交通量の多い場所では控える、など）
- 電池の消費

## 第三者の媒体・広告の再生

場所に紐づく外部のコンテンツ（観光協会の音声ガイド、店舗の紹介、イベント告知、広告など）を、その場所に近づいたときに再生・表示する。

- [ ] コンテンツの形式（音声・動画・画像・テキスト・リンク）
- [ ] 配信の仕組み（コンテンツと位置・期間・対象範囲を登録するサーバーが必要）
- [ ] 提供者が登録する方法（管理画面、または提携先からのデータ取り込み）
- [ ] 広告であることの明示と、ガイドの解説と混同させない表示
- [ ] 表示頻度の上限（散策の邪魔にならないように）
- [ ] 設定で広告をオフにできるか、有料プランとの関係

決めること:
- 収益化の方針（広告、有料プラン、提携）
- 広告配信のために位置情報を外部に送るかどうか。送る場合は同意の取得とプライバシーポリシーの更新が必要（現在は「緯度経度や経路は AI に送らない」方針）
- 既存の広告 SDK を使うか、自前で配信するか
- 第三者のコンテンツの審査（不適切な内容・虚偽の防止）

## 位置に紐づく秘密メッセージ

特定の場所に来たときだけ読める・聞けるメッセージ。ジオキャッシュのように、場所に「置いて」おき、その場所に来た人が見つける。

利用場面の例:
- 自分宛て: 「1 年後にまたここに来たら読む」メッセージ
- 家族・友人宛て: 特定の人だけが開けるメッセージ
- 公開: その場所を訪れた人なら誰でも見つけられる（宝探し、イベント）
- 第三者の媒体（上記）と組み合わせた、店舗やイベントの隠しコンテンツ

- [ ] メッセージを置く（現在地、または地図上の地点を指定）
- [ ] 開ける条件（半径◯m 以内、日時・期間、特定の相手、合言葉）
- [ ] 近くに来たら通知し、話しかけで知らせる
- [ ] 形式（テキスト・音声・写真）
- [ ] 自分宛てだけなら端末内で完結、他人宛てならサーバーと本人確認が必要

自分宛てだけならサーバーなしで作れる（`HistoryStore` と同じく端末内に保存）。先にここだけ切り出して着手できる。

決めること:
- 位置の偽装（位置情報の偽装アプリ）で開けられることへの対策をどこまでやるか
- 公開メッセージの不適切な投稿への対策（通報・削除）
- 私有地・危険な場所に置かせない配慮
- サーバーを持つかどうか（他の項目とも共通の判断）

## 共通の検討事項

- **サーバーの要否**: 第三者の媒体・他人宛ての秘密メッセージはサーバーが必要。現在のアプリはサーバーを持たず、端末と公開 API だけで動いている。項目ごとにばらばらに決めず、1 つの判断（ADR）としてまとめて決める。
- **プライバシー**: 位置情報を外部に送る範囲が広がる。README の「散歩の記録の扱い」を更新し、同意を取る。
- **安全**: 歩きながら画面を見させない。音声中心の案内を基本にする。
- **電池・通信量**: 画像・音声の取得と再生が増えるため、散策モードでの消費を計測する。天気の取得は 15 分ごとに増やした（予報の取得のため）。
- **公開サーバーの負荷**: Overpass・Open-Meteo は公開サーバーを使っている。取得する項目と頻度が増えてきたので、利用者が増える前に利用ポリシーを確認し、自前のサーバーや商用のサービスを検討する。
