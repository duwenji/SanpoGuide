## 契約要約
- 利用者: SanpoGuide アプリ（Android）。サーバーは利用者が URL で指定する（自前のサーバーも可）
- 入力: 署名付きの封筒（本文・位置は端末で暗号化）、公開鍵、暗号化した添付
- 出力: 封筒の一覧（受信箱・地域別の公開メッセージ）、公開鍵
- エラー: RFC 9457 + `code`（docs/secret-messages-api.md のエラー表）
- 互換性方針: パスで版を分ける（/v1）、項目の追加は互換、暗号方式は `suite` で分ける

## 段階記録

### Phase 1（段階1〜6）
- 実施内容: TODO.md の要件、既存の設定（GuideSettings.customBaseUrl、KeyCipher）、minSdk 26 の制約を確認し、契約案を作成
- 判断根拠:
  - E2E 暗号化にしてサーバーを信用しなくてよい形にした（URL で任意のサーバーを指定できるため）
  - Ed25519/X25519 は minSdk 26 の Keystore で使えないため、Tink のキーセットを Keystore の AES 鍵で暗号化して保存する
  - direct メッセージは受信箱を位置で絞らず取得し、サーバーに位置を渡さない
- 比較した案:
  - 認証: A. チャレンジ→短期トークン（採用案）／B. リクエストごとの署名（RFC 9421）／C. パスワード＋メール（鍵の方針に反するため不採用）
  - 位置の扱い: A. 位置も暗号化し、端末で判定（採用案）／B. サーバーに正確な位置を渡し、サーバーで判定（プライバシー方針に反する）／C. サーバーに大まかな位置だけ渡す（公開メッセージのみ採用）
  - 公開メッセージの鍵: A. 場所＋合言葉から導出（採用案）／B. 暗号化しない／C. サーバーが位置確認後に鍵を渡す（偽装対策を強めたい場合の将来案）
- 承認ステータス: 段階7（契約案の決定）待ち。未決事項 No.2・3 の回答が必要

### Phase 1 追補（v0.2: 管理と配信フィルター）
- 実施内容: 開発者の要望「サーバーでメッセージ管理と配信、配信は Filter 機能を持つ」を受けて契約案を拡張
- 判断根拠:
  - フィルターに使う情報は署名付きヘッダー（サーバーは読めるが書き換えられない）、本文と正確な位置は暗号文、と区分して E2E 暗号化と両立させた
  - フィルターは「送り手の配信条件」と「受け手の受信フィルター」の両方を同じ式で表し、両方に合うときだけ配信する
  - 式は項目・演算子を限定した JSON にし、知らない項目はエラーにする（黙って無視すると意図より広く配信されるため）
  - 「近くに来たら配信」はサーバーで判定しない（正確な位置を送らない方針のため）
  - 自前サーバーは FCM を直接使えないため、プッシュは poll / relay / unifiedpush の 3 方式にした
- 比較した案:
  - フィルターの表現: A. 限定した JSON の式（採用案）／B. SQL 風の文字列（実装が重く、注入の危険）／C. 固定の項目の組み合わせのみ（柔軟性が足りない）
  - public の判定時期: A. 取得時に判定（採用案）／B. 置いたときに全員へ配る（受け手の位置が分からないため不可）
- 承認ステータス: 段階7（契約案の決定）待ち。未決事項 No.2・3・4・5 の回答が必要

### 段階7（契約案の決定）
- 実施内容: 開発者が未決事項に回答
- 決定:
  - D-1 第 1 版は direct・group・受信フィルター・管理（状態・版・配信状況）。public・配信条件・publisher・運営 API は第 2 版
  - D-2 認証はチャレンジ署名→短期トークン
  - D-3 プッシュは poll と UnifiedPush のみ（中継サーバーは運営しない）
  - D-4 配信条件に使える受け手の属性は言語と興味のみ
- 承認者: 開発者（2026-09-29）
- 承認ステータス: 承認

### 段階14（最終報告）
- 決定内容: API-001 1.0 を承認。第 1 版は direct・group・受信フィルター・管理。認証はチャレンジ署名→短期トークン。プッシュは poll と UnifiedPush。配信条件の属性は言語と興味。サーバーは準拠していれば実装・置き場所を問わず、アプリは URL で選ぶ
- 互換性: `/v1` のまま第 2 版の機能を足し、`features` で対応状況を知らせる。未対応の機能は `unsupported_feature`
- 残課題: 鍵のバックアップ、第 1 版の通報対応手順、publisher の審査、複数端末、プライバシーポリシー、参照実装のサーバー、OpenAPI と準拠テスト
- 次のステップ: OpenAPI の作成と準拠テスト → 参照実装のサーバー → アプリの実装（feature-implementation-unified）
