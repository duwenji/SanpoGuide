## 比較表

| 案 | 利点 | 欠点 | 判定 |
|----|------|------|------|
| 1. 審査なし・アプリ側の上限のみ | 運用の負担がない。配信元が自由 | 不適切な語り口・宣伝を防げない | 不採用 |
| 2. 配信元の署名のみ | 身元が分かる。運用の負担がない | 内容の判断を利用者に任せる | 不採用 |
| 3. 運用者の審査と署名＋アプリ側の上限＋取り下げ | 署名で確かめられる。置き場所を問わない | 審査の手間。運用者の鍵の管理 | 採用 |
| 4. 運用者のストアのサーバーからだけ取得 | 一元管理 | サーバーの運用と信用が要る。API-001 D-5 の考え方に反する | 不採用 |
| 5. 組み込みのチャンネルだけ | 安全・簡単 | 要件を満たさない | 不採用 |

## 段階記録

### Phase 1（段階1〜6）

- 実施内容: チャンネルの要件（TODO.md「チャンネル」、2026-10-03 の決定）と、API-001 の鍵・D-5、プロンプトの構成（prompts.md）を確認した。第三者のチャンネルの問題を「費用・内容の安全性・出どころ」の 3 つに整理し、案 1〜5 を比較した
- 判断根拠: 第三者のプロンプトは利用者の API キーで動く。AI の返答は毎回違うので、審査だけでは散歩中の発言を保証できない
- 承認ステータス: 完了

### Phase 2（段階7〜8）

- 実施内容: 開発者が「システム運用者が品質を担保し、基準を満たしたチャンネルのみ取り込む」方針を提示した。Claude は、それを成り立たせるための補足（運用者の署名、アプリ側の上限の維持、失効リスト、審査基準の文書化）を提案した。開発者が「進んで」と回答したので、案 3 で ADR の草案を作成した
- 判断根拠: 署名にすれば置き場所を信用しなくてよく、専用のサーバーも要らない。審査で防げないものはアプリ側の上限と取り下げで補う
- 承認ステータス: 段階7 は決定済み（2026-10-03）。段階9（草案の承認）待ち

### Phase 3（段階10〜12）

- 実施内容: 実装・運用・テスト・移行・保守・プライバシーの影響、追従タスク T-1〜T-6、見直しの条件を ADR に記載した
- 承認ステータス: 段階11（観点の承認）・段階13（最終承認）待ち。未決事項 No.1（運用者は誰か）は承認時に回答が必要
